## Records / receipts / payouts recon findings (2026-09-22)

Read-only recon after the account-delete work shipped. Question posed:
Stripe is the permanent system-of-record for the money itself — what
business context does ONLY MCC hold, how does MCC link to Stripe, and does
all of it survive account deletion?

### Stripe linkage

Money is safe in Stripe. Most paths have a durable **two-way link**:
Stripe metadata carries MCC ids (care_plan_id / member_id / provider_id /
etc.) AND MCC stores the resulting Stripe id. Job↔payment tie for care
plans specifically survives account deletion because
`care_plans.stripe_payment_intent_id` is NOT scrubbed by `_anonymizeJobRecords`.

Minor **one-way gaps** — Stripe knows, MCC can't answer without hitting the
Stripe API:
- Package crowdfund contributions (`package-contribute.js`) — PI id
  returned to client only, no MCC writeback.
- Support donations (`support-donation.js`) — no MCC-side table at all.
- Ride provider-subsidy PI (`transport-request.js:419`) — charge succeeds,
  PI id discarded.

Notes on drift:
- `payments` legacy table has FOUR Stripe-id columns
  (`stripe_payment_intent`, `stripe_payment_intent_id`, `stripe_payment_id`,
  `stripe_transfer_id`); `member-release-payment.js` reads three as
  fallbacks. Historical accretion, not broken, but any canonical PI-lookup
  must consider all three.
- `care_plan_completions.stripe_payment_intent_id` column exists but **no
  code writes it** — completion → Stripe is a two-hop via
  `care_plan_id → care_plans.stripe_payment_intent_id`. Two-hop is
  deletion-safe. Direct column is cosmetic.

### Deletion-safe (confirmed by recon)

- Job ↔ payment tie (`care_plans.stripe_payment_intent_id` retained).
- Service line items on care_plans: `title, services, service_types,
  categories, value_min/max, state` retained.
- Member + provider name snapshots on `care_plan_completions`
  (`member_name_snapshot`, `provider_business_name_snapshot`) — WRITTEN by
  the deployed anonymize pass. Read paths must consult them; see gap #3
  below for a code-only gap.
- Completion money fields: `bid_amount, actual_paid_amount, payment_method,
  completion_notes, founder_transfer_id` all preserved.

### NOT SAFE — sole-copy gaps found

Ranked:

   `account-deletion-core.js:44` `.delete().eq('founder_id', ...)` on

## Rollback DDL for `20260921h` + `20260921i`

Kept in-hand; recording here so it survives the session. Reverse-order safe.
Includes pre-flight abort if any row has null counterparty (would be lost by
restoring NOT NULL).

```sql
BEGIN;

-- ---------------------------------------------------------------------------
-- PRE-FLIGHT — abort if any row has a nulled counterparty. Restoring NOT NULL
-- on such rows would either fail (which is fine) or, if you also blindly
-- deleted them, lose data. Do not proceed unless this returns zero.
-- ---------------------------------------------------------------------------
DO $rollback_guard$
DECLARE
  n_care_plans_null              int;
  n_plan_bids_null               int;
  n_completions_member_null      int;
  n_completions_provider_null    int;
BEGIN
  SELECT count(*) INTO n_care_plans_null
    FROM public.care_plans WHERE member_id IS NULL;
  SELECT count(*) INTO n_plan_bids_null
    FROM public.plan_bids  WHERE provider_id IS NULL;
  SELECT count(*) INTO n_completions_member_null
    FROM public.care_plan_completions WHERE member_id IS NULL;
  SELECT count(*) INTO n_completions_provider_null
    FROM public.care_plan_completions WHERE provider_id IS NULL;

  IF n_care_plans_null > 0
     OR n_plan_bids_null > 0
     OR n_completions_member_null > 0
     OR n_completions_provider_null > 0 THEN
    RAISE EXCEPTION
      'rollback aborted — nulled counterparties exist (care_plans=%, plan_bids=%, completions.member=%, completions.provider=%). Delete or repair those rows first.',
      n_care_plans_null, n_plan_bids_null,
      n_completions_member_null, n_completions_provider_null;
  END IF;
END
$rollback_guard$;

-- ---------------------------------------------------------------------------
-- 1. Drop triggers first (from 20260921i). Order doesn't strictly matter but
--    dropping triggers before CHECKs avoids any theoretical UPDATE mid-rollback
--    firing them.
-- ---------------------------------------------------------------------------
DROP TRIGGER IF EXISTS trg_care_plans_stamp_member_deleted_at            ON public.care_plans;
DROP TRIGGER IF EXISTS trg_plan_bids_stamp_provider_deleted_at           ON public.plan_bids;
DROP TRIGGER IF EXISTS trg_care_plan_completions_stamp_member_deleted_at ON public.care_plan_completions;

DROP FUNCTION IF EXISTS public.care_plans_stamp_member_deleted_at()            CASCADE;
DROP FUNCTION IF EXISTS public.plan_bids_stamp_provider_deleted_at()           CASCADE;
DROP FUNCTION IF EXISTS public.care_plan_completions_stamp_member_deleted_at() CASCADE;

-- ---------------------------------------------------------------------------
-- 2. Drop CHECK constraints (from 20260921h). Names below match what 20260921h
--    created (verify against pg_constraint before running if unsure).
-- ---------------------------------------------------------------------------
ALTER TABLE public.care_plans
  DROP CONSTRAINT IF EXISTS care_plans_member_link_or_deleted;
ALTER TABLE public.plan_bids
  DROP CONSTRAINT IF EXISTS plan_bids_provider_link_or_deleted;
ALTER TABLE public.care_plan_completions
  DROP CONSTRAINT IF EXISTS care_plan_completions_member_link_or_deleted;
ALTER TABLE public.care_plan_completions
  DROP CONSTRAINT IF EXISTS care_plan_completions_provider_link_or_deleted;

-- ---------------------------------------------------------------------------
-- 3. Drop indexes (from 20260921h).
-- ---------------------------------------------------------------------------
DROP INDEX IF EXISTS public.idx_care_plans_member_deleted_at;
DROP INDEX IF EXISTS public.idx_care_plan_completions_member_deleted_at;

-- ---------------------------------------------------------------------------
-- 4. Drop snapshot columns and *_deleted_at columns (from 20260921h).
-- ---------------------------------------------------------------------------
ALTER TABLE public.care_plans              DROP COLUMN IF EXISTS member_deleted_at;
ALTER TABLE public.plan_bids               DROP COLUMN IF EXISTS provider_deleted_at;
ALTER TABLE public.care_plan_completions   DROP COLUMN IF EXISTS member_deleted_at;
ALTER TABLE public.care_plan_completions   DROP COLUMN IF EXISTS provider_deleted_at;
ALTER TABLE public.care_plan_completions   DROP COLUMN IF EXISTS member_name_snapshot;
ALTER TABLE public.care_plan_completions   DROP COLUMN IF EXISTS provider_business_name_snapshot;

-- ---------------------------------------------------------------------------
-- 5. Restore FKs to ON DELETE CASCADE + NOT NULL (from 20260921h). FK names
--    below are the originals restored by 20260921h; verify against
--    pg_constraint if unsure. This is the dangerous step: it re-enables the
--    data-loss cascade. Only run if you understand the consequences.
```

- **Member request on completed care-plan job** — hook `members-packages.js:5032 requestRefund()` into a real button on completed packages, or replace it entirely. `www/members-packages.js:4928 openRefundModal()` and `submitRefundRequest()` are orphaned right now (POST to `/api/escrow/refund/:packageId` which does not exist).
